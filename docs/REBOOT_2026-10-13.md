# Obelisk: revisión y nuevo objetivo

Fecha: 2026-10-13. El operador pide revisar lo recuperable y reformular el
proyecto hacia plugins nativos de ARK: Survival Evolved para Linux.

Este documento conserva la revisión inicial. El estado activo está en
`OPING_PROTOTYPE.md`: la instalación y el adaptador han migrado a la rama
public para clientes Steam/Epic, y preaquatica, recovered y las compilaciones
duplicadas se han eliminado. Las rutas antiguas de esta revisión son historia;
el ZIP original conserva el trabajo recuperado.

## Ubicaciones

- Proyecto activo: `/servidor/obelisk/Obelisk`, copia física del código recuperado
  con el trabajo histórico sin descartar cambios sin commit.
- Archivo original: `/servidor/ark/obelisk-project-archive.zip`.
- Recuperación conservada: `/servidor/ark/obelisk-lab/recovered`.
- Laboratorio de servidor y herramientas: `/servidor/ark/obelisk-lab`.
- REA: paquete oficial `rea-agents`, versión fijada 6.4.0, con Ghidra 12.1 y JDK 21.

El código activo queda fuera de la raíz de servidores porque varios scripts
históricos rechazan cualquier entrada bajo `/servidor/ark`. Esos scripts también
conservan rutas absolutas de servidores y evidencias que ya no existen.

## Lo comprobado hoy

1. Código recuperado compilado desde cero; CTest: 141/141 pruebas correctas.
2. ASE nativo Linux instalado mediante SteamCMD, rama `preaquatica`, build
   13834083, descarga y validación correctas. Ocupa aproximadamente 17,6 GiB.
3. SHA256 instalado:
   `951a5977922dfe0eb1a4e153abdad7127f0b3602391f93904160387dfd1593cb`.
   Es diferente del binario histórico `7e7ded49...`.
4. Firma de ProcessEvent encontrada una sola vez en segmento ejecutable:
   dirección virtual `0x1d10130`; la histórica era `0x1d34e20`.
5. Prueba con el servidor real: LD_PRELOAD, instalación del hook de 18 bytes,
   carga de `oProcessTimer.so` y ejecución de su callback confirmadas en logs.
6. REA: diagnóstico correcto, MCP inicializado y conexión al binario actual.
   Backend Ghidra comprobado con un ejecutable pequeño. El análisis dirigido
   del ARK actual se guarda como evidencia estática, sin inventar validación UE.

Ghidra decompiló ambos candidatos en unos 11 segundos por binario, sin análisis
global ni prototipo inyectado. Recuperó 657 bytes por función, tres argumentos
inferidos y los primeros 64 bytes iguales. Esto respalda la candidatura del hook;
no demuestra por sí solo el layout de UObject/UFunction ni equivalencia completa.
Comparación: `/servidor/ark/obelisk-lab/logs/ghidra-process-event-comparison.json`.

Evidencia de ejecución:
`/servidor/ark/obelisk-lab/logs/runtime-smoke-result.json` y
`/servidor/ark/obelisk-lab/logs/ark-smoke-console.log`.

El servidor de prueba se detuvo. No se observó el callback de shutdown ni la
retirada del hook: no está demostrada la limpieza durante cierre. Tampoco se
demostró mapa listo, jugadores, chat, identidad, comandos, respuestas o gameplay.
La prueba demuestra el núcleo de plugins, no una SDK equivalente a ArkApi.
Para próximas pruebas locales usar el launcher de red privada: MultiHome por sí
solo no restringió los sockets secundarios de Steam.
La segunda prueba confirmó red privada, carga del hook y callback; se detuvo
después. Evidencia: `/servidor/ark/obelisk-lab/logs/smoke-network-isolation.json`.

## Qué conservar

- Loader LD_PRELOAD y logging.
- Descubrimiento por firma única y comprobación del prólogo antes de parchear.
- ABI C versionada, metadatos, carga dlopen y configuración de plugins.
- Ownership y copia de datos en la frontera pública.
- Pruebas de ABI, dispatch, configuración y timers; fixtures de lectores cuando
  se demuestre que corresponden al binario.
- Investigación y herramientas útiles, conservando su procedencia histórica.

## Qué reformular

- Un perfil por binario verificado realmente. La selección histórica por una
  variable de entorno con el SHA antiguo no demuestra la identidad del proceso.
- No recargar ni retirar hooks durante ejecución en el primer hito. La retirada
  manual actual no protege a todos los hilos que pueden ejecutar el prólogo.
- Revisar Memory::IsReadable: su cache puede conservar permisos antiguos y no
  demuestra que un UObject siga vivo.
- Introducir un estado explícito de disponibilidad del juego antes de exponer
  operaciones gameplay. Los timers actuales ejecutan en un worker, no en UE.
- Convertir los documentos y gates de promoción en información de estado;
  avanzar mediante una función real verificable. Hay 346 archivos de scripts
  y 327 de documentación, pero todavía no existe Reply en la SDK pública.
- Un comando abierto a todos no requiere implementar previamente todo el
  sistema de administración y permisos. Sí requiere identificar y validar la
  sesión a la que se responde.

## Próximo hito: oPing

1. Identificar en este binario la ruta que recibe el chat y la ruta que envía
   una respuesta al cliente; corroborar con Ghidra/REA y observación limitada.
2. Correlacionar el ShooterPlayerController real con una identidad de sesión
   válida. Mantener punteros UE privados; invalidar el destino al desconectar.
3. Implementar un adaptador Linux mínimo y una API de plugin para recibir el
   comando y responder desde el hilo adecuado del juego.
4. Crear `oPing.so`, con `/ping` disponible para todos y respuesta `pong`.
5. Verificar con clientes reales: responde solo al emisor, distingue dos
   jugadores y rechaza una sesión anterior tras desconexión/reconexión.

Después ampliar administración, permisos, inventario y economía por necesidad
de plugins concretos. No diseñar doce módulos completos antes de demostrar el
primer recorrido funcional. Los plugins serán nativos Linux `.so`; la
compatibilidad binaria con DLL de Windows no forma parte de este hito.
